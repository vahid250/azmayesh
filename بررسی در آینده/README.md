# بررسی در آینده — دفتر پیگیری فنی R&MA

این پوشه محل ثبت تصمیم‌ها و کارهای فنیِ عمداً به‌تعویق‌افتاده است تا بین گفتگوها و مراحل اجرا فراموش نشوند.

## روش نگهداری

- هر مورد وضعیت، شرط شروع و نتیجهٔ بررسی دارد.
- پیش از رسیدن به شرط شروع، مورد را تغییر ندهید یا زودتر اجرا نکنید.
- پس از بررسی، نتیجه و تاریخ را همین‌جا ثبت کنید؛ مورد را بی‌صدا حذف نکنید.
- موارد حساس مانند تغییر دیتابیس، تنظیمات اجرایی و Deploy نیازمند تأیید صریح کاربر هستند.
- این دفتر جایگزین تست یا مستندات اجرایی نیست؛ فهرست پیگیری و یادآوری تصمیم‌هاست.

## موارد باز

### 1. بازبینی سیاست Caching در Cloudflare Hyperdrive
- **وضعیت:** ⏳ نیازمند بررسی
- **شرط شروع:** پیش از اتصال API واقعی و استفاده از داده‌های حساب/اشتراک.
- **وضعیت فعلی شناخته‌شده:** پیکربندی `rma-neon-production`؛ Max Age برابر ۶۰ ثانیه و Stale While Revalidate برابر ۱۵ ثانیه گزارش شده است.
- **کار بررسی:** مشخص‌کردن اینکه چه queryهایی ممکن است cache شوند، بررسی سازگاری cache با داده‌های کاربر و تغییرات سریع، و تعیین سیاست امن برای queryهای حساس. در صورت نیاز، خاموش‌کردن caching یا تنظیم مناسب‌تر فقط پس از بررسی مستندات و تأیید کاربر.
- **یادداشت:** صرف وجود این مقادیر به معنی فعال‌بودن یا مناسب‌بودن cache برای همهٔ queryها نیست؛ رفتار دقیق باید با مستندات جاری Cloudflare و الگوی queryهای برنامه تطبیق داده شود.

### 2. تأیید اتصال واقعی Worker به Neon از طریق Hyperdrive
- **وضعیت:** ⏳ نیازمند بررسی
- **شرط شروع:** پس از افزودن Hyperdrive binding به پیکربندی Worker و پیش از Deploy عمومی.
- **کار بررسی:** تأیید binding با نام مورد انتظار، تست اتصال امن و read-only به دیتابیس، و بررسی خطاها و latency.
- **شناسهٔ Hyperdrive:** `22ea3c86d6a842d2a57415dc16dc1b66`
- **نام پیکربندی:** `rma-neon-production`
- **یادداشت امنیتی:** Connection String، رمز عبور و کلیدها نباید در Git یا گفتگو ثبت شوند.

### 3. سازگاری وابستگی‌های Python با Cloudflare Python Workers
- **وضعیت:** ⏳ نیازمند بررسی
- **شرط شروع:** پیش از اتکا به Worker به‌عنوان میزبان backend.
- **کار بررسی:** آزمون واقعی بسته‌های موردنیاز، به‌ویژه `cryptography` و درایور PostgreSQL انتخاب‌شده، در محیط Python Workers؛ بررسی محدودیت‌های WASM و روش تزریق bindingها به تنظیمات برنامه.
- **یادداشت:** موفقیت dry-run بسته‌بندی به‌تنهایی اثبات اجرای موفق همهٔ وابستگی‌ها در زمان اجرا نیست.

### 4. اجرای کنترل‌شدهٔ Database Migrations
- **وضعیت:** ⏳ نیازمند بررسی
- **شرط شروع:** پس از تأیید اتصال دیتابیس و پیش از فعال‌سازی مسیرهای API نیازمند schema.
- **کار بررسی:** بازبینی migrationها، تهیهٔ برنامهٔ بازگشت/بازیابی، اجرای جدا از startup Worker و تأیید نتیجه.
- **محدودیت:** هیچ migration یا SQL تغییردهنده بدون تأیید صریح کاربر اجرا نشود.

### 5. تکمیل تنظیمات امن و آزمون API واقعی
- **وضعیت:** ⏳ نیازمند بررسی
- **شرط شروع:** پس از موفقیت آزمون runtime و اتصال Neon.
- **کار بررسی:** تنظیم secrets فقط در پنل امن Cloudflare، حفظ `MOCK_MODE=true` تا آماده‌شدن زیرساخت واقعی، آزمون Telegram initData و endpointهای سلامت، و سپس برنامه‌ریزی Deploy با تأیید جداگانه.
- **یادداشت:** تا زمان وجود سرویس مستقل WireGuard، هیچ اتصال VPN واقعی یا handshake نباید ادعا شود.

- `MOCK_MODE=true` باید تا آماده‌شدن زیرساخت واقعی حفظ شود.

### 6. راه‌اندازی سرویس مستقل WireGuard
- **وضعیت:** ⏳ نیازمند طراحی و اجرا در آینده
- **شرط شروع:** پس از پایدارشدن API و اتصال Neon؛ این سرویس نباید داخل Cloudflare Python Worker اجرا شود.
- **کار بررسی و پیاده‌سازی:** انتخاب یک میزبان مستقل مناسب برای WireGuard؛ طراحی API امن و محدود میان R&MA Worker و سرویس WireGuard؛ مدیریت ساخت، ثبت، مشاهدهٔ وضعیت و لغو peerها؛ نگهداری امن کلیدهای خصوصی؛ و طراحی firewall، مسیریابی، DNS و محدودیت دسترسی.
- **آزمون پذیرش:** تأیید ثبت peer روی سرور، مشاهدهٔ handshake واقعی، افزایش شمارنده‌های RX/TX، و آزمون DNS و HTTPS از سمت کلاینت.
- **محدودیت امنیتی:** اجرای فرمان‌های `wg`، `subprocess` و دسترسی به رابط شبکه فقط روی میزبان مستقل انجام شود؛ Worker صرفاً از طریق ارتباط احراز هویت‌شده و محدود با آن سرویس صحبت کند.
- **یادداشت:** تا زمانی که آزمون‌های انتهابه‌انتها موفق نشده‌اند، فایل کانفیگ آزمایشی به‌معنی VPN فعال یا اتصال اینترنتی نیست.
