# گزارش سخت‌سازی امنیت API و احراز هویت R&MA

تاریخ: ۱۷ نوامبر ۲۰۲۶  
وضعیت: نشست مستقل در شاخه آزمایشی پیاده‌سازی و CI آن موفق شده است؛ هنوز برای محیط عملیاتی تأیید یا مستقر نشده است.

## کنترل‌های پیاده‌سازی‌شده

- اعتبارسنجی امضای Telegram WebApp با HMAC و مقایسه امن امضا.
- رد فیلدهای تکراری، داده‌های ناقص، hash با قالب نامعتبر، auth_date غیرعددی و payload بزرگ‌تر از حد مجاز.
- محدود کردن تعداد فیلدهای initData به ۳۲ مورد پیش از بررسی امضا.
- اجباری بودن شیء user و شناسه عددی صحیح و مثبت Telegram؛ شناسه بولی، رشته‌ای، صفر و منفی پذیرفته نمی‌شود.
- رد زمان آینده بیش از ۳۰ ثانیه و محدود کردن عمر مجاز initData به حداکثر یک ساعت. مقدار پیش‌فرض تنظیمات نیز یک ساعت است.
- کلید API آزمایشگاهی فقط خارج از production فعال است؛ مقایسه نام محیط بدون حساسیت به بزرگی/کوچکی حروف انجام می‌شود تا مقدار Production نیز به اشتباه مسیر آزمایشگاهی را باز نکند.
- پاسخ‌های مسیرهای API و webhook با Cache-Control: no-store، X-Content-Type-Options، X-Frame-Options، Referrer-Policy و Permissions-Policy محافظت می‌شوند.
- مسیرهای خصوصی پس از تبادل اولیه فقط Bearer session می‌پذیرند؛ ارسال مستقیم X-Telegram-Init-Data به مسیر خصوصی رد می‌شود. کلید API آزمایشگاهی فقط در development/test قابل استفاده است.
- مسیر `POST /api/v1/auth/session` ابتدا امضای Telegram initData را بررسی و سپس نشست مستقل صادر می‌کند؛ مسیر `POST /api/v1/auth/logout` نشست جاری را ابطال می‌کند.
- توکن نشست ۲۵۶ بیتی با HMAC-SHA256 و کلید محرمانه مستقل مشتق می‌شود. فقط SHA-256 توکن در جدول `user_sessions` ذخیره می‌شود؛ مقدار خام توکن در دیتابیس نگهداری نمی‌شود.
- کلید تبادل تصادفی ۲۵۶ بیتی در مرورگر فقط برای idempotency در sessionStorage می‌ماند و به هش initData همان بازشدن Mini App متصل است؛ access token فقط در حافظه JavaScript نگهداری می‌شود.
- عمر مطلق نشست ۴ ساعت، مهلت بیکاری ۳۰ دقیقه و به‌روزرسانی `last_seen_at` حداکثر هر ۵ دقیقه است. ابطال سمت سرور در هر درخواست Bearer بررسی می‌شود.
- مسیرهای سفارش و اشتراک بر اساس شناسه کاربر احراز‌شده فیلتر می‌شوند؛ مسیرهای کانفیگ WireGuard نیز مالکیت رکورد را پیش از ارائه کانفیگ، وضعیت یا لغو بررسی می‌کنند.

## مواردی که هنوز نباید ادعای حل‌شدنشان را داشته باشیم

### بازپخش initData و چرخه عمر نشست

مسیرهای خصوصی دیگر initData خام را نمی‌پذیرند؛ فقط مسیر تبادل نشست آن را دریافت و امضای Telegram را بررسی می‌کند. با این حال، خود مسیر تبادل می‌تواند در پنجره اعتبار initData هدف حمله بازپخش قرار گیرد؛ محدودسازی نرخ توزیع‌شده و سیاست ضدسوءاستفاده برای این مسیر هنوز باید در Cloudflare WAF/Rate Limiting تنظیم شود.

کلید محرمانه مستقل با نام `RMA_SESSION_DERIVATION_KEY` برای Worker الزامی است و باید حداقل ۳۲ بایت تصادفی مستقل داشته باشد. این کلید نباید با Bot Token، کلید Fernet یا کلید Metering یکسان باشد و نباید در Git، متغیر عمومی Wrangler یا مرورگر قرار گیرد. در اجرای Render نام متغیر محیطی متناظر `SESSION_DERIVATION_KEY` است. بدون این کلید، تبادل نشست با پاسخ 503 و به‌صورت fail-closed متوقف می‌شود.

نسخه فعلی فقط نسخه کلید ۱ را می‌شناسد. چرخش کلید باید با برنامه‌ریزی نسخه‌های قبلی یا ابطال کنترل‌شده همه نشست‌ها انجام شود؛ چرخش خودکار هنوز پیاده‌سازی نشده است. توکن Bearer در حافظه JavaScript نگهداری می‌شود، اما XSS همچنان می‌تواند از نشست فعال سوءاستفاده کند؛ سخت‌سازی CSP و جلوگیری از XSS پیش از عرضه الزامی است.

### محدودسازی نرخ درخواست‌ها

محدودسازی توزیع‌شده درخواست‌ها در این مرحله به‌صورت سراسری در برنامه فعال نشده است. محدودکننده حافظه‌ای داخل یک Worker برای چند نمونه یا چند منطقه قابل اتکا نیست. پیش از عرضه باید Cloudflare Rate Limiting/WAF برای مسیرهای ورود، مسیرهای عمومی، webhook و عملیات حساس تنظیم و در محیط واقعی آزموده شود. تنظیمات واقعی Cloudflare از این شاخه یا CI قابل تأیید نیست.

### آزمون عملیاتی

موفقیت GitHub Actions فقط آزمون کد و بسته‌بندی در CI را اثبات می‌کند. این نتیجه به معنی آزمون Cloudflare واقعی، نشست واقعی Telegram، پیکربندی WAF، استقرار یا آمادگی production نیست.

## مرز ایمنی

تمام تغییرات در شاخه آزمایشی `rebuild/rma-hardening-from-dashboard` باقی می‌مانند. هیچ deploy، تغییر در `main`، مهاجرت روی دیتابیس اصلی، دریافت وجه یا فعال‌سازی سرور VPN در این مرحله انجام نشده است.
