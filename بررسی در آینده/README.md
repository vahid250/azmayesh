# بررسی در آینده — دفتر پیگیری فنی R&MA

این پوشه محل ثبت تصمیم‌ها و کارهای فنیِ عمداً به‌تعویق‌افتاده است تا بین گفتگوها و مراحل اجرا فراموش نشوند.

## روش نگهداری

- هر مورد وضعیت، شرط شروع و نتیجهٔ بررسی دارد.
- پیش از رسیدن به شرط شروع، مورد را تغییر ندهید یا زودتر اجرا نکنید.
- پس از بررسی، نتیجه و تاریخ را همین‌جا ثبت کنید؛ مورد را بی‌صدا حذف نکنید.
- موارد حساس مانند تغییر دیتابیس، تنظیمات اجرایی و Deploy نیازمند تأیید صریح کاربر هستند.
- این دفتر جایگزین تست یا مستندات اجرایی نیست؛ فهرست پیگیری و یادآوری تصمیم‌هاست.

## موارد باز

### 1. بازبینی سیاست Caching در Cloudflare Hyperdrive
- **وضعیت:** ⏳ نیازمند بررسی
- **شرط شروع:** پیش از اتصال API واقعی و استفاده از داده‌های حساب/اشتراک.
- **وضعیت فعلی شناخته‌شده:** پیکربندی `rma-neon-production`؛ Max Age برابر ۶۰ ثانیه و Stale While Revalidate برابر ۱۵ ثانیه گزارش شده است.
- **کار بررسی:** مشخص‌کردن اینکه چه queryهایی ممکن است cache شوند، بررسی سازگاری cache با داده‌های کاربر و تغییرات سریع، و تعیین سیاست امن برای queryهای حساس. در صورت نیاز، خاموش‌کردن caching یا تنظیم مناسب‌تر فقط پس از بررسی مستندات و تأیید کاربر.
- **یادداشت:** صرف وجود این مقادیر به معنی فعال‌بودن یا مناسب‌بودن cache برای همهٔ queryها نیست؛ رفتار دقیق باید با مستندات جاری Cloudflare و الگوی queryهای برنامه تطبیق داده شود.

### 2. تأیید اتصال واقعی Worker به Neon از طریق Hyperdrive
- **وضعیت:** ⏳ نیازمند بررسی
- **شرط شروع:** پس از افزودن Hyperdrive binding به پیکربندی Worker و پیش از Deploy عمومی.
- **کار بررسی:** تأیید binding با نام مورد انتظار، تست اتصال امن و read-only به دیتابیس، و بررسی خطاها و latency.
- **شناسهٔ Hyperdrive:** `22ea3c86d6a842d2a57415dc16dc1b66`
- **نام پیکربندی:** `rma-neon-production`
- **یادداشت امنیتی:** Connection String، رمز عبور و کلیدها نباید در Git یا گفتگو ثبت شوند.

### 3. سازگاری وابستگی‌های Python با Cloudflare Python Workers
- **وضعیت:** ⏳ نیازمند بررسی
- **شرط شروع:** پیش از اتکا به Worker به‌عنوان میزبان backend.
- **کار بررسی:** آزمون واقعی بسته‌های موردنیاز، به‌ویژه `cryptography` و درایور PostgreSQL انتخاب‌شده، در محیط Python Workers؛ بررسی محدودیت‌های WASM و روش تزریق bindingها به تنظیمات برنامه.
- **یادداشت:** موفقیت dry-run بسته‌بندی به‌تنهایی اثبات اجرای موفق همهٔ وابستگی‌ها در زمان اجرا نیست.

### 4. اجرای کنترل‌شدهٔ Database Migrations
- **وضعیت:** ⏳ نیازمند بررسی
- **شرط شروع:** پس از تأیید اتصال دیتابیس و پیش از فعال‌سازی مسیرهای API نیازمند schema.
- **کار بررسی:** بازبینی migrationها، تهیهٔ برنامهٔ بازگشت/بازیابی، اجرای جدا از startup Worker و تأیید نتیجه.
- **محدودیت:** هیچ migration یا SQL تغییردهنده بدون تأیید صریح کاربر اجرا نشود.

### 5. تکمیل تنظیمات امن و آزمون API واقعی
- **وضعیت:** ⏳ نیازمند بررسی
- **شرط شروع:** پس از موفقیت آزمون runtime و اتصال Neon.
- **کار بررسی:** تنظیم secrets فقط در پنل امن Cloudflare، حفظ `MOCK_MODE=true` تا آماده‌شدن زیرساخت واقعی، آزمون Telegram initData و endpointهای سلامت، و سپس برنامه‌ریزی Deploy با تأیید جداگانه.
- **یادداشت:** تا زمان وجود سرویس مستقل WireGuard، هیچ اتصال VPN واقعی یا handshake نباید ادعا شود.

## وضعیت زیرساخت در زمان ایجاد این دفتر

- مخزن: `vahid250/azmayesh`
- شاخهٔ کاری: `work/rma-backend-dashboard`
- Hyperdrive با نام `rma-neon-production` ساخته شده است.
- هنوز اتصال Worker به Hyperdrive، اجرای migration و Deploy عمومی تأیید نشده‌اند.
- `MOCK_MODE=true` باید تا آماده‌شدن زیرساخت واقعی حفظ شود.

### 6. راه‌اندازی سرویس مستقل WireGuard
- **وضعیت:** ⏳ نیازمند طراحی و اجرا در آینده
- **شرط شروع:** پس از پایدارشدن API و اتصال Neon؛ این سرویس نباید داخل Cloudflare Python Worker اجرا شود.
- **کار بررسی و پیاده‌سازی:** انتخاب یک میزبان مستقل مناسب برای WireGuard؛ طراحی API امن و محدود میان R&MA Worker و سرویس WireGuard؛ مدیریت ساخت، ثبت، مشاهدهٔ وضعیت و لغو peerها؛ نگهداری امن کلیدهای خصوصی؛ و طراحی firewall، مسیریابی، DNS و محدودیت دسترسی.
- **آزمون پذیرش:** تأیید ثبت peer روی سرور، مشاهدهٔ handshake واقعی، افزایش شمارنده‌های RX/TX، و آزمون DNS و HTTPS از سمت کلاینت.
- **محدودیت امنیتی:** اجرای فرمان‌های `wg`، `subprocess` و دسترسی به رابط شبکه فقط روی میزبان مستقل انجام شود؛ Worker صرفاً از طریق ارتباط احراز هویت‌شده و محدود با آن سرویس صحبت کند.
- **یادداشت:** تا زمانی که آزمون‌های انتهابه‌انتها موفق نشده‌اند، فایل کانفیگ آزمایشی به‌معنی VPN فعال یا اتصال اینترنتی نیست.

### 7. چرخهٔ بازخورد کیفیت و یادگیری از خطاهای کانفیگ
- **وضعیت:** ⏳ نیازمند طراحی و پیاده‌سازی
- **شرط شروع:** پس از راه‌اندازی سرویس مستقل WireGuard و فراهم‌شدن آزمون‌های واقعی؛ در حالت MOCK فقط خطاهای شبیه‌سازی‌شده قابل ثبت‌اند.
- **هدف:** هر خطای معتبرِ کشف‌شده در تولید یا آزمون کانفیگ، به گزارش ساخت‌یافته و قابل اقدام برای سازنده تبدیل شود تا علت ریشه‌ای اصلاح و در تولیدهای بعدی از تکرار آن جلوگیری شود.
- **چرخهٔ پیشنهادی:** تولید کانفیگ با شناسه و نسخهٔ سازنده ← اجرای آزمون‌های خودکار ← ثبت نتیجه و شواهد فنیِ پالایش‌شده ← دسته‌بندی و تحلیل علت ریشه‌ای ← اصلاح الگو/قواعد تولید ← اجرای مجدد آزمون‌های رگرسیون ← انتشار نسخهٔ جدید پس از عبور از معیارهای پذیرش.
- **الزامات:** تفکیک خطای واقعی از اختلال موقت شبکه و خطای محیط آزمون؛ ثبت نسخهٔ generator، نسخهٔ الگوی کانفیگ، نوع آزمون، مرحلهٔ شکست، کد خطا، زمان و نتیجهٔ تکرار؛ جلوگیری از ارسال گزارش تکراری و اولویت‌بندی بر اساس شدت و تکرار.
- **حفاظت داده:** هیچ private key، رمز، توکن، connection string یا دادهٔ هویتی کاربر در گزارش‌ها ذخیره یا ارسال نشود. گزارش‌ها باید حداقل‌گرا، پالایش‌شده و قابل ردیابی با شناسهٔ داخلی باشند.
- **معیار موفقیت:** کاهش نرخ خطاهای تکرارشونده در نسخه‌های بعدی، افزایش نرخ قبولی آزمون‌های رگرسیون و حفظ امکان بازگشت به نسخهٔ سالم قبلی.
- **یادداشت:** گزارش خطا به‌تنهایی به معنی اصلاح خودکار و امن نیست؛ تغییر قواعد تولید باید نسخه‌بندی، بازبینی و با مجموعهٔ آزمون ثابت تأیید شود. برای جزئیات طراحی ضمانت، عودت و چرخهٔ یادگیری به سند `docs/RMA_CONFIG_WARRANTY_AND_REFUNDS.md` مراجعه شود.

### 8. طراحی کاتالوگ سفارش کانفیگ و سفارش‌ساز دستی
- **وضعیت:** ⏳ نیازمند طراحی محصول، قیمت‌گذاری و پیاده‌سازی
- **هدف:** فراهم‌کردن دو مسیر سفارش در ربات: بسته‌های آماده و سفارش‌ساز دستی برای کاربران حرفه‌ای یا نیازهای خاص.

#### مسیر اول: بسته‌های آماده برای کاربر
- حجم‌های پایهٔ پیشنهادی: ۱ گیگابایت، ۱۰ گیگابایت، ۵۰ گیگابایت و ۱۰۰ گیگابایت.
- مدت‌های پیشنهادی: روزانه، ماهانه و سالانه.
- هر ترکیب حجم/مدت فقط وقتی در کاتالوگ نمایش داده شود که قیمت، ظرفیت، محدودیت منصفانه و موجودی/قابلیت ارائهٔ آن مشخص و تأیید شده باشد.
- بسته‌ها باید به زبان ساده شامل حجم کل، زمان شروع و پایان اعتبار، سیاست مصرف منصفانه، نوع اتصال/پروتکل و شرایط پشتیبانی باشند.
- بستهٔ رایگان یا آزمایشی، در صورت ارائه، باید کیفیت فنی و امنیت پایهٔ برابر با بسته‌های پولی داشته باشد.

#### مسیر دوم: سفارش‌ساز دستی
- نوع سرویس/پروتکل: WireGuard یا سرویس‌های مبتنی بر V2Ray؛ قالب یا برنامهٔ مقصد (برای مثال NapsternetV) به‌عنوان گزینه‌ای جداگانه و فقط در صورت سازگاری واقعی.
- حجم قابل انتخاب: حداقل ۵۰۰ مگابایت؛ سقف اولیهٔ پیشنهادی برای نسخهٔ نخست ۵۰۰ گیگابایت به‌ازای هر سفارش. سفارش‌های بزرگ‌تر از این سقف فقط با بررسی ظرفیت و تأیید مدیر قابل ارائه باشند.
- مدت‌ها: روزانه، هفتگی، یک‌ماهه، دوماهه، سه‌ماهه، شش‌ماهه و یک‌ساله.
- اعتبارسنجی ترکیب حجم و مدت ضروری است؛ مثلاً سفارش حجم بسیار بالا با مدت کوتاه یا حجم کم با مدت طولانی باید با سیاست ظرفیت و قیمت‌گذاری سازگار باشد.
- پیش از پرداخت/صدور، خلاصهٔ سفارش شامل نوع سرویس، قالب کلاینت، حجم، مدت، قیمت، محدودیت‌ها و شرایط ضمانت به کاربر نمایش داده شود.
- سفارش‌ساز باید گزینه‌های نامعتبر یا غیرقابل ارائه را پنهان یا غیرفعال کند و هرگز سفارش را صرفاً بر اساس ورودی آزاد و بدون اعتبارسنجی تولید نکند.

#### نکات معماری و فنی
- کاتالوگ بسته‌ها و قواعد قیمت‌گذاری از منطق تولید کانفیگ جدا باشند؛ تغییر قیمت نباید نیازمند تغییر generator باشد.
- مدل داده باید محصول/پلن، سفارش، پرداخت، صدور سرویس، نوع پروتکل، قالب کلاینت، سهمیهٔ حجم، مدت، زمان شروع/انقضا و وضعیت را پوشش دهد.
- برای حجم، مقدار عددی استاندارد مانند بایت ذخیره شود؛ نمایش GB/GiB در رابط کاربری باید شفاف و یکسان باشد.
- مصرف و سهمیهٔ باقی‌مانده فقط وقتی نمایش داده شود که شمارندهٔ معتبر از سرویس واقعی قابل دریافت باشد؛ مقدار ساختگی در MOCK_MODE ممنوع است.
- برای هر سفارش، سیاست تمدید، اتمام حجم، پایان مدت، توقف/تعلیق و لغو باید از پیش تعریف شود.
- پنل مدیر می‌تواند سفارش دستی را ایجاد یا تنظیم کند، اما صدور باید پس از اعتبارسنجی ظرفیت، قیمت، سازگاری پروتکل/کلاینت و وضعیت پرداخت انجام شود.
- این مورد فعلاً صرفاً طراحی آینده است؛ قیمت‌گذاری، موجودی سرورها، سرویس واقعی V2Ray و WireGuard و پرداخت هنوز فعال/تأییدشده نیستند.
