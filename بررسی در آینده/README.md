# بررسی در آینده — دفتر پیگیری فنی R&MA

این پوشه محل ثبت تصمیم‌ها و کارهای فنیِ عمداً به‌تعویق‌افتاده است تا بین گفتگوها و مراحل اجرا فراموش نشوند.

## روش نگهداری

- هر مورد وضعیت، شرط شروع و نتیجهٔ بررسی دارد.
- پیش از رسیدن به شرط شروع، مورد را تغییر ندهید یا زودتر اجرا نکنید.
- پس از بررسی، نتیجه و تاریخ را همین‌جا ثبت کنید؛ مورد را بی‌صدا حذف نکنید.
- موارد حساس مانند تغییر دیتابیس، تنظیمات اجرایی و Deploy نیازمند تأیید صریح کاربر هستند.
- این دفتر جایگزین تست یا مستندات اجرایی نیست؛ فهرست پیگیری و یادآوری تصمیم‌هاست.

## موارد باز

### 1. بازبینی سیاست Caching در Cloudflare Hyperdrive
- **وضعیت:** ⏳ نیازمند بررسی
- **شرط شروع:** پیش از اتصال API واقعی و استفاده از داده‌های حساب/اشتراک.
- **وضعیت فعلی شناخته‌شده:** پیکربندی `rma-neon-production`؛ Max Age برابر ۶۰ ثانیه و Stale While Revalidate برابر ۱۵ ثانیه گزارش شده است.
- **کار بررسی:** مشخص‌کردن اینکه چه queryهایی ممکن است cache شوند، بررسی سازگاری cache با داده‌های کاربر و تغییرات سریع، و تعیین سیاست امن برای queryهای حساس. در صورت نیاز، خاموش‌کردن caching یا تنظیم مناسب‌تر فقط پس از بررسی مستندات و تأیید کاربر.
- **یادداشت:** صرف وجود این مقادیر به معنی فعال‌بودن یا مناسب‌بودن cache برای همهٔ queryها نیست؛ رفتار دقیق باید با مستندات جاری Cloudflare و الگوی queryهای برنامه تطبیق داده شود.

### 2. تأیید اتصال واقعی Worker به Neon از طریق Hyperdrive
- **وضعیت:** ⏳ نیازمند بررسی
- **شرط شروع:** پس از افزودن Hyperdrive binding به پیکربندی Worker و پیش از Deploy عمومی.
- **کار بررسی:** تأیید binding با نام مورد انتظار، تست اتصال امن و read-only به دیتابیس، و بررسی خطاها و latency.
- **شناسهٔ Hyperdrive:** `22ea3c86d6a842d2a57415dc16dc1b66`
- **نام پیکربندی:** `rma-neon-production`
- **یادداشت امنیتی:** Connection String، رمز عبور و کلیدها نباید در Git یا گفتگو ثبت شوند.

### 3. سازگاری وابستگی‌های Python با Cloudflare Python Workers
- **وضعیت:** ⏳ نیازمند بررسی
- **شرط شروع:** پیش از اتکا به Worker به‌عنوان میزبان backend.
- **کار بررسی:** آزمون واقعی بسته‌های موردنیاز، به‌ویژه `cryptography` و درایور PostgreSQL انتخاب‌شده، در محیط Python Workers؛ بررسی محدودیت‌های WASM و روش تزریق bindingها به تنظیمات برنامه.
- **یادداشت:** موفقیت dry-run بسته‌بندی به‌تنهایی اثبات اجرای موفق همهٔ وابستگی‌ها در زمان اجرا نیست.

### 4. اجرای کنترل‌شدهٔ Database Migrations
- **وضعیت:** ⏳ نیازمند بررسی
- **شرط شروع:** پس از تأیید اتصال دیتابیس و پیش از فعال‌سازی مسیرهای API نیازمند schema.
- **کار بررسی:** بازبینی migrationها، تهیهٔ برنامهٔ بازگشت/بازیابی، اجرای جدا از startup Worker و تأیید نتیجه.
- **محدودیت:** هیچ migration یا SQL تغییردهنده بدون تأیید صریح کاربر اجرا نشود.

### 5. تکمیل تنظیمات امن و آزمون API واقعی
- **وضعیت:** ⏳ نیازمند بررسی
- **شرط شروع:** پس از موفقیت آزمون runtime و اتصال Neon.
- **کار بررسی:** تنظیم secrets فقط در پنل امن Cloudflare، حفظ `MOCK_MODE=true` تا آماده‌شدن زیرساخت واقعی، آزمون Telegram initData و endpointهای سلامت، و سپس برنامه‌ریزی Deploy با تأیید جداگانه.
- **یادداشت:** تا زمان وجود سرویس مستقل WireGuard، هیچ اتصال VPN واقعی یا handshake نباید ادعا شود.

## وضعیت زیرساخت در زمان ایجاد این دفتر

- مخزن: `vahid250/azmayesh`
- شاخهٔ کاری: `work/rma-backend-dashboard`
- Hyperdrive با نام `rma-neon-production` ساخته شده است.
- هنوز اتصال Worker به Hyperdrive، اجرای migration و Deploy عمومی تأیید نشده‌اند.
- `MOCK_MODE=true` باید تا آماده‌شدن زیرساخت واقعی حفظ شود.

### 6. راه‌اندازی سرویس مستقل WireGuard
- **وضعیت:** ⏳ نیازمند طراحی و اجرا در آینده
- **شرط شروع:** پس از پایدارشدن API و اتصال Neon؛ این سرویس نباید داخل Cloudflare Python Worker اجرا شود.
- **کار بررسی و پیاده‌سازی:** انتخاب یک میزبان مستقل مناسب برای WireGuard؛ طراحی API امن و محدود میان R&MA Worker و سرویس WireGuard؛ مدیریت ساخت، ثبت، مشاهدهٔ وضعیت و لغو peerها؛ نگهداری امن کلیدهای خصوصی؛ و طراحی firewall، مسیریابی، DNS و محدودیت دسترسی.
- **آزمون پذیرش:** تأیید ثبت peer روی سرور، مشاهدهٔ handshake واقعی، افزایش شمارنده‌های RX/TX، و آزمون DNS و HTTPS از سمت کلاینت.
- **محدودیت امنیتی:** اجرای فرمان‌های `wg`، `subprocess` و دسترسی به رابط شبکه فقط روی میزبان مستقل انجام شود؛ Worker صرفاً از طریق ارتباط احراز هویت‌شده و محدود با آن سرویس صحبت کند.
- **یادداشت:** تا زمانی که آزمون‌های انتهابه‌انتها موفق نشده‌اند، فایل کانفیگ آزمایشی به‌معنی VPN فعال یا اتصال اینترنتی نیست.

### 7. چرخهٔ بازخورد کیفیت و یادگیری از خطاهای کانفیگ
- **وضعیت:** ⏳ نیازمند طراحی و پیاده‌سازی
- **شرط شروع:** پس از راه‌اندازی سرویس مستقل WireGuard و فراهم‌شدن آزمون‌های واقعی؛ در حالت MOCK فقط خطاهای شبیه‌سازی‌شده قابل ثبت‌اند.
- **هدف:** هر خطای معتبرِ کشف‌شده در تولید یا آزمون کانفیگ، به گزارش ساخت‌یافته و قابل اقدام برای سازنده تبدیل شود تا علت ریشه‌ای اصلاح و در تولیدهای بعدی از تکرار آن جلوگیری شود.
- **چرخهٔ پیشنهادی:** تولید کانفیگ با شناسه و نسخهٔ سازنده ← اجرای آزمون‌های خودکار ← ثبت نتیجه و شواهد فنیِ پالایش‌شده ← دسته‌بندی و تحلیل علت ریشه‌ای ← اصلاح الگو/قواعد تولید ← اجرای مجدد آزمون‌های رگرسیون ← انتشار نسخهٔ جدید پس از عبور از معیارهای پذیرش.
- **الزامات:** تفکیک خطای واقعی از اختلال موقت شبکه و خطای محیط آزمون؛ ثبت نسخهٔ generator، نسخهٔ الگوی کانفیگ، نوع آزمون، مرحلهٔ شکست، کد خطا، زمان و نتیجهٔ تکرار؛ جلوگیری از ارسال گزارش تکراری و اولویت‌بندی بر اساس شدت و تکرار.
- **حفاظت داده:** هیچ private key، رمز، توکن، connection string یا دادهٔ هویتی کاربر در گزارش‌ها ذخیره یا ارسال نشود. گزارش‌ها باید حداقل‌گرا، پالایش‌شده و قابل ردیابی با شناسهٔ داخلی باشند.
- **معیار موفقیت:** کاهش نرخ خطاهای تکرارشونده در نسخه‌های بعدی، افزایش نرخ قبولی آزمون‌های رگرسیون و حفظ امکان بازگشت به نسخهٔ سالم قبلی.
- **یادداشت:** گزارش خطا به‌تنهایی به معنی اصلاح خودکار و امن نیست؛ تغییر قواعد تولید باید نسخه‌بندی، بازبینی و با مجموعهٔ آزمون ثابت تأیید شود. برای جزئیات طراحی ضمانت، عودت و چرخهٔ یادگیری به سند `docs/RMA_CONFIG_WARRANTY_AND_REFUNDS.md` مراجعه شود.

### 8. طراحی کاتالوگ سفارش کانفیگ و سفارش‌ساز دستی
- **وضعیت:** ⏳ نیازمند طراحی محصول، قیمت‌گذاری و پیاده‌سازی
- **هدف:** فراهم‌کردن دو مسیر سفارش در ربات: بسته‌های آماده و سفارش‌ساز دستی برای کاربران حرفه‌ای یا نیازهای خاص.

#### مسیر اول: بسته‌های آماده برای کاربر
- حجم‌های پایهٔ پیشنهادی: ۱ گیگابایت، ۱۰ گیگابایت، ۵۰ گیگابایت و ۱۰۰ گیگابایت.
- مدت‌های پیشنهادی: روزانه، ماهانه و سالانه.
- هر ترکیب حجم/مدت فقط وقتی در کاتالوگ نمایش داده شود که قیمت، ظرفیت، محدودیت منصفانه و موجودی/قابلیت ارائهٔ آن مشخص و تأیید شده باشد.
- بسته‌ها باید به زبان ساده شامل حجم کل، زمان شروع و پایان اعتبار، سیاست مصرف منصفانه، نوع اتصال/پروتکل و شرایط پشتیبانی باشند.
- بستهٔ رایگان یا آزمایشی، در صورت ارائه، باید کیفیت فنی و امنیت پایهٔ برابر با بسته‌های پولی داشته باشد.

#### مسیر دوم: سفارش‌ساز دستی
- نوع سرویس/پروتکل: انتخاب سرویس WireGuard یا V2Ray؛ برنامه/قالب کلاینت در این مسیر از کاربر پرسیده نشود و بر اساس سازگاری فنی در مرحلهٔ تحویل تعیین شود.
- NapsternetV پروتکل نیست؛ فقط در بسته‌های پیش‌فرض و به‌عنوان قالب/کلاینت تحویل، آن هم در صورت سازگاری واقعی، نمایش داده شود.
- حجم قابل انتخاب: حداقل ۵۰۰ مگابایت؛ سقف اولیهٔ پیشنهادی برای نسخهٔ نخست ۵۰۰ گیگابایت به‌ازای هر سفارش. سفارش‌های بزرگ‌تر از این سقف فقط با بررسی ظرفیت و تأیید مدیر قابل ارائه باشند.
- مدت‌ها: روزانه، هفتگی، یک‌ماهه، دوماهه، سه‌ماهه، شش‌ماهه و یک‌ساله.
- اعتبارسنجی ترکیب حجم و مدت ضروری است؛ مثلاً سفارش حجم بسیار بالا با مدت کوتاه یا حجم کم با مدت طولانی باید با سیاست ظرفیت و قیمت‌گذاری سازگار باشد.
- پیش از پرداخت/صدور، خلاصهٔ سفارش شامل نوع سرویس، حجم، مدت، قیمت، محدودیت‌ها و شرایط ضمانت به کاربر نمایش داده شود.
- سفارش‌ساز باید گزینه‌های نامعتبر یا غیرقابل ارائه را پنهان یا غیرفعال کند و هرگز سفارش را صرفاً بر اساس ورودی آزاد و بدون اعتبارسنجی تولید نکند.

#### فرایند هفت‌مرحله‌ای سفارش بستهٔ پیش‌فرض
۱. انتخاب بسته و حجم؛ ۲. انتخاب مدت؛ ۳. انتخاب قالب/کلاینت سازگار (از جمله NapsternetV فقط در صورت پشتیبانی)؛ ۴. بررسی ظرفیت و قابلیت ارائه؛ ۵. نمایش پیش‌فاکتور، محدودیت‌ها و ضمانت؛ ۶. پرداخت و پیگیری وضعیت؛ ۷. صدور اختصاصی و تحویل همراه راهنمای اتصال.
- این هفت مرحله مخصوص مسیر بسته‌های پیش‌فرض است و به‌معنای هفت سطح کیفیت یا هفت نوع کانفیگ نیست.

#### نکات معماری و فنی
- کاتالوگ بسته‌ها و قواعد قیمت‌گذاری از منطق تولید کانفیگ جدا باشند؛ تغییر قیمت نباید نیازمند تغییر generator باشد.
- مدل داده باید محصول/پلن، سفارش، پرداخت، صدور سرویس، نوع پروتکل، قالب کلاینت، سهمیهٔ حجم، مدت، زمان شروع/انقضا و وضعیت را پوشش دهد.
- برای حجم، مقدار عددی استاندارد مانند بایت ذخیره شود؛ نمایش GB/GiB در رابط کاربری باید شفاف و یکسان باشد.
- مصرف و سهمیهٔ باقی‌مانده فقط وقتی نمایش داده شود که شمارندهٔ معتبر از سرویس واقعی قابل دریافت باشد؛ مقدار ساختگی در MOCK_MODE ممنوع است.
- برای هر سفارش، سیاست تمدید، اتمام حجم، پایان مدت، توقف/تعلیق و لغو باید از پیش تعریف شود.
- پنل مدیر می‌تواند سفارش دستی را ایجاد یا تنظیم کند، اما صدور باید پس از اعتبارسنجی ظرفیت، قیمت، سازگاری پروتکل/کلاینت و وضعیت پرداخت انجام شود.
- این مورد فعلاً صرفاً طراحی آینده است؛ قیمت‌گذاری، موجودی سرورها، سرویس واقعی V2Ray و WireGuard و پرداخت هنوز فعال/تأییدشده نیستند.


### 9. مخزن آماده‌سازی پیشاپیش برای صدور سریع
- **وضعیت:** ⏳ نیازمند طراحی و بررسی امنیتی
- **هدف:** شناسایی الگوهای پرتکرار سفارش و آماده‌سازی پیشاپیش منابع و مراحل غیرمحرمانهٔ صدور برای کاهش زمان انتظار کاربر.
- **اصل امنیتی:** کانفیگ خامِ دارای هویت، کلید خصوصی یا اعتبارنامه نباید به‌صورت مشترک میان کاربران ذخیره یا واگذار شود. هیچ کانفیگ یا کلید اختصاصی نباید از یک کاربر به کاربر دیگر منتقل شود.
- **طرح بررسی:** بررسی cache برای metadata و الگوهای بی‌خطر، آماده‌سازی ظرفیت/آدرس‌های قابل تخصیص در محدودهٔ مجاز، و تولید کلید و کانفیگ نهایی اختصاصی پس از احراز هویت، کنترل مالکیت، ظرفیت و وضعیت سفارش.
- **کار بررسی:** تعیین TTL، قفل تخصیص، جلوگیری از تخصیص هم‌زمان یک منبع، پاک‌سازی منابع منقضی و معیارهای عدم استفاده از دادهٔ حساس در cache.
- **شرط شروع:** پس از طراحی چرخهٔ سفارش و صدور و فراهم‌شدن سرویس واقعی؛ تا آن زمان صرفاً طراحی و آزمون شبیه‌سازی‌شده.

### 10. حافظهٔ موقت، کنترل فرمان‌های تکراری و صف صدور
- **وضعیت:** ⏳ نیازمند بررسی معماری و هزینه
- **هدف:** پایش فرمان‌ها و کلیک‌های تکراری یا هم‌زمان، جلوگیری از ثبت/صدور چندباره و محافظت از generator در برابر فشار ناگهانی.
- **طرح بررسی:** ارزیابی Cloudflare Durable Objects برای وضعیت هماهنگ‌شده و قفل/محدودسازی per-user، Cloudflare Queues برای صف‌بندی و کنترل نرخ پردازش، و استفاده از شناسهٔ idempotency در API و دیتابیس.
- **الزامات:** پیام تکراری نباید عملیات صدور را تکرار کند؛ سفارش مستقل و معتبر با مشخصات متفاوت نباید به‌اشتباه حذف شود؛ وضعیت در حال پردازش به کاربر نمایش داده شود؛ صف باید retry، dead-letter و بازیابی پس از خطا داشته باشد.
- **نکتهٔ فنی:** حافظهٔ محلی یک Worker به‌تنهایی منبع هماهنگ‌کنندهٔ سراسری و پایدار نیست. رفتار تحویل حداقل یک‌بارهٔ صف و احتمال دریافت پیام تکراری باید در طراحی لحاظ شود.
- **کار بررسی:** مستندات و محدودیت‌های جاری پلن رایگان، هزینهٔ احتمالی، سقف throughput، TTL، رفتار خرابی و نیازهای نگهداری داده بررسی شوند.
- **شرط شروع:** پیش از فعال‌سازی سفارش واقعی و صدور خودکار.

### 11. رهگیری تأیید تراکنش‌های ارز دیجیتال و زمان تقریبی
- **وضعیت:** ⏳ نیازمند طراحی و بررسی ارائه‌دهندهٔ پرداخت
- **هدف:** نمایش پیشرفت واقعی تراکنش و کاهش کلیک/سفارش تکراری هنگام انتظار تأیید شبکه.
- **طرح وضعیت:** منتظر پرداخت، تراکنش شناسایی‌شده، در انتظار تأیید شبکه، تأییدهای میانی، تأیید نهایی، ناموفق/نیازمند بررسی.
- **الزامات:** ذخیرهٔ شناسهٔ تراکنش، شبکه و دارایی، تعداد تأییدهای دریافت‌شده و موردنیاز، زمان‌های مشاهده و تأیید، و رویدادهای تغییر وضعیت؛ پردازش callback/webhook باید امضای معتبر و idempotency داشته باشد.
- **نمایش زمان:** فقط بر اساس دادهٔ شبکه/ارائه‌دهنده و سیاست تأیید همان دارایی و شبکه، بازهٔ تقریبی نمایش داده شود؛ زمان تخمینی تضمین نیست و در نبود دادهٔ معتبر باید صرفاً وضعیت «در حال بررسی» نمایش داده شود.
- **شرط شروع:** پس از انتخاب ارائه‌دهنده/درگاه و مشخص‌شدن شبکه‌ها، سیاست تأیید، callback و روش تطبیق پرداخت.

### 12. بازبینی تجربهٔ سفارش هفت‌مرحله‌ای بسته‌های پیش‌فرض
- **وضعیت:** ⏳ نیازمند طراحی UI و آزمون کاربری
- **هدف:** اجرای مسیر هفت‌مرحله‌ای: انتخاب بسته/حجم، انتخاب مدت، انتخاب قالب کلاینت سازگار، بررسی ظرفیت، پیش‌فاکتور و ضمانت، پرداخت و پیگیری، صدور و تحویل.
- **مرزبندی:** این هفت مرحله فقط برای سفارش بسته‌های پیش‌فرض است؛ سفارش‌ساز دستی مسیر مستقل و ساده‌تری دارد و NapsternetV در فهرست پروتکل‌های آن نمایش داده نمی‌شود.
- **کار بررسی:** ارزیابی تعداد کلیک‌ها، امکان بازگشت مرحله‌ای، حفظ وضعیت سفارش، جلوگیری از پرداخت/ثبت چندباره، نمایش پیشرفت و دسترس‌پذیری روی موبایل و Telegram Mini App.
- **شرط شروع:** پس از تثبیت مدل سفارش، بسته‌ها، قیمت‌گذاری و وضعیت‌های پرداخت/صدور.


### 13. نهایی‌سازی و آزمون سیاست بازپرداخت و تعویض کانفیگ
- **وضعیت:** ⏳ نیازمند طراحی، پیاده‌سازی و آزمون
- **تصمیم محصول:** بازپرداخت انصراف فقط وقتی مجاز است که درخواست حداکثر تا ۲۴ ساعت پس از خرید ثبت شود، کانفیگ در هیچ دستگاهی فعال نشده باشد و مصرف ثبت‌شده دقیقاً صفر باشد.
- **مقصد بازپرداخت:** فقط همان آدرس مبدأ پرداخت؛ تغییر آدرس مقصد به درخواست کاربر مجاز نیست. برای پرداخت‌های رمزارزی باید پیش از انتخاب درگاه روشن شود که آدرس مبدأ واقعاً به کیف پول تحت کنترل پرداخت‌کننده تعلق دارد یا آدرس تجمیعی صرافی/پرداخت‌یار است. در حالت آدرس تجمیعی، باید روش امن و قابل‌اثباتی برای بازگشت وجه به همان پرداخت‌کننده طراحی شود؛ بازفرستادن کورکورانه به آدرس داغ صرافی ممکن است وجه را به کاربر نرساند.
- **هزینهٔ انتقال:** هزینهٔ واقعی و قابل‌اثبات انتقال بازپرداخت بر عهدهٔ کاربر است و مبلغ خالص و کارمزد پیش از تأیید نهایی شفاف اعلام می‌شوند؛ هزینهٔ پنهان یا دلخواه ممنوع است.
- **خرابی پس از فعال‌سازی/مصرف:** اگر کانفیگ مصرف شده یا در دستگاهی فعال شده باشد و بعداً به علت فنی از کار بیفتد، مسیر بازپرداخت انصراف اعمال نمی‌شود. پس از تأیید خرابی، کانفیگ تعویض و با همان حجم باقی‌مانده و همان مدت اعتبار باقی‌مانده تحویل می‌شود؛ زمان اعتبار از نو آغاز نمی‌شود و حق مشتری کاهش نمی‌یابد.
- **الزامات فنی:** ثبت زمان خرید و درخواست، وضعیت فعال‌سازی در تمام دستگاه‌های مجاز، شمارندهٔ مصرف معتبر و قابل حسابرسی، تاریخ انقضای اصلی، شناسهٔ سفارش/تراکنش و مقصد پرداخت. در نبود دادهٔ معتبر فعال‌سازی یا مصرف، سامانه نباید به‌صورت خودکار واجدشرایط‌بودن بازپرداخت را ادعا کند؛ درخواست باید برای بررسی دستی متوقف شود.
- **کنترل امنیتی:** ثبت و تطبیق مسیر پرداخت و بازپرداخت، جلوگیری از بازپرداخت تکراری با idempotency، نگهداری سوابق حسابرسی و بررسی موارد مشکوک.
- **شرط شروع:** پس از وجود صدور واقعی، accounting معتبر مصرف، ثبت رویداد فعال‌سازی و انتخاب روش پرداخت/بازپرداخت؛ تا آن زمان این قواعد صرفاً سیاست طراحی هستند و نباید به‌عنوان قابلیت فعال تبلیغ شوند.

### 14. تدوین یک قانون‌نامهٔ جامع، کوتاه و قابل‌فهم با تأیید کاربر
- **وضعیت:** ⏳ نیازمند طراحی محتوا، تجربهٔ کاربری و پیاده‌سازی
- **هدف:** تهیهٔ یک متن واحد، جامع، منصفانه و قابل‌فهم که قواعد اصلی استفاده از R&MA را روشن کند و کاربر پیش از شروع استفاده آن را مطالعه و صریحاً تأیید کند.
- **اصل تجربهٔ کاربری:** از متن‌های طولانی، تکراری، حقوقیِ پیچیده و صفحه‌هایی که کاربر برای رسیدن به بند پایانی مجبور به اسکرول بی‌پایان است پرهیز شود. قانون‌نامه باید تا حد امکان کوتاه، روشن، دسته‌بندی‌شده و بدون تکرار باشد؛ کوتاهی نباید باعث حذف حق یا تعهد مهم شود.
- **دامنهٔ محتوا:** ماهیت و حدود سرویس؛ شرایط ثبت‌نام و مسئولیت حساب؛ امنیت و حفاظت اطلاعات؛ خرید، پرداخت و صدور؛ حجم و مدت اعتبار؛ محدودیت‌ها و استفادهٔ مجاز؛ پشتیبانی و رسیدگی به خرابی؛ سیاست دقیق بازپرداخت و تعویض؛ تعلیق/لغو و رسیدگی به سوءاستفاده؛ تغییرات قانون‌نامه و راه ارتباط با پشتیبانی.
- **طراحی پیشنهادی:** یک قانون‌نامهٔ اصلی با تیترهای کوتاه و زبان ساده، نمایش خلاصهٔ نکات حیاتی پیش از تأیید، و امکان بازکردن جزئیات هر بخش در صورت نیاز؛ نه چند سند پراکنده و نه متن تکراری. کاربر باید بتواند متن کامل را نیز به‌سادگی مشاهده کند.
- **تأیید آگاهانه:** شروع استفاده یا ثبت سفارش منوط به اقدام مثبت کاربر برای پذیرش نسخهٔ مشخص قانون‌نامه باشد؛ گزینهٔ ازپیش‌علامت‌خورده یا پذیرش ضمنی از طریق صرفاً ادامه‌دادن ممنوع. در صورت نپذیرفتن، کاربر بتواند خارج شود و سرویس نیازمند پذیرش را استفاده نکند.
- **ثبت سابقه:** شناسه/نسخه و هش قانون‌نامه، شناسهٔ حساب تلگرام، زمان UTC، و نتیجهٔ پذیرش ثبت شود. در صورت تغییر اساسی شرایط، نسخهٔ جدید نمایش داده شود و پذیرش مجدد پیش از ادامهٔ استفاده لازم باشد. فقط دادهٔ حداقلی لازم نگهداری شود.
- **معیار پذیرش:** متن توسط کاربر عادی قابل فهم باشد؛ حقوق و تعهدات دو طرف، به‌ویژه شرایط بازپرداخت و تعویض، بدون ابهام بیان شوند؛ روی موبایل و Telegram Mini App خوانا باشد؛ و هیچ قابلیت پیاده‌سازی‌نشده به‌عنوان خدمت فعال وعده داده نشود.
- **شرط شروع:** پیش از عرضهٔ عمومی/تجاری و پیش از فعال‌سازی پذیرش اجباری؛ متن نهایی باید با قابلیت‌های واقعی محصول و الزامات قانونی محل فعالیت تطبیق داده و به تأیید کاربر برسد.
